# Root Cause 分析

根據 Jira issue 或問題敘述，深入追蹤程式碼找出根本原因，提出解決方案。**不會直接實作**，專注於分析與方案設計。

## 快速使用

使用 Jira Issue Key：
```bash
/analyze-root-cause EK-1000
```

使用 Jira URL：
```bash
/analyze-root-cause https://showyouapp.atlassian.net/browse/EK-1000
```

直接描述問題：
```bash
/analyze-root-cause 使用者刪除帳號後重新登入，無法顯示設定暱稱頁面
```

不提供參數（會提示輸入）：
```bash
/analyze-root-cause
```

## 執行流程

### 1. 收集問題資訊

**如果提供 Jira Issue Key / URL：**
- 使用 Jira MCP server (`mcp__jira-extended__jira_get_issue`) 獲取 issue 詳細資訊
- 提取：Summary、Description、Issue Type、重現步驟、Comments、Attachments
- 如果 issue 有附圖（截圖、螢幕錄影），會特別注意 UI 相關的線索

**如果提供文字敘述：**
- 解析問題描述，提取關鍵資訊
- 識別可能涉及的功能模組和程式碼區域
- 如有不清楚的地方，主動詢問使用者補充

### 2. 定位相關程式碼

- 根據問題描述中的關鍵字（頁面名稱、功能名稱、錯誤訊息等），使用 `Grep` 和 `Glob` 搜尋相關程式碼
- 使用 `Read` 讀取並理解涉及的檔案
- 建立程式碼地圖：哪些檔案、類別、函數與問題相關

### 3. 深入追蹤執行路徑

這是核心步驟，會從多個角度追蹤問題：

#### 3a. 正向追蹤（從觸發點開始）
- 從使用者操作（按鈕點擊、頁面進入等）開始
- 追蹤 UI → ViewModel → UseCase → Repository → API 的呼叫鏈
- 記錄每一步的資料流和狀態變化

#### 3b. 反向追蹤（從異常結果回推）
- 從「不正確的行為」出發
- 往上追蹤是哪個判斷、哪個資料導致了這個結果
- 找出「應該是 A 但實際是 B」的分歧點

#### 3c. 比對分析（正常 vs 異常路徑）
- 比較正常情況和異常情況的程式碼路徑差異
- 找出哪個條件/狀態在異常情況下不同
- 確認是邏輯錯誤、狀態殘留、時序問題、還是其他原因

### 4. 確認根本原因

找到可疑點後，進行驗證：
- 確認這個原因能解釋**所有**的異常行為
- 排除其他可能的原因
- 如果有多個可能的 root cause，全部列出並評估可能性

### 5. 設計解決方案

針對 root cause 提出解決方案：

- **如果只有一個最佳方案**：直接說明修改內容和原因
- **如果有多個可行方案**：列出每個方案的優缺點，讓使用者選擇
- 每個方案都會包含：
  - 需要修改的檔案和位置
  - 具體的修改內容
  - 可能的風險和副作用
  - 影響範圍評估

### 6. 輸出分析報告

以結構化格式呈現分析結果：

```
🔍 Root Cause 分析報告

📋 問題描述：
{問題的簡要描述}

🔄 重現步驟：
1. {步驟 1}
2. {步驟 2}
3. ...

🎯 根本原因：
{清楚說明 root cause 是什麼，為什麼會發生}

📁 涉及檔案與程式碼：
- {檔案路徑}:{行號範圍} — {這段程式碼的作用}
- {檔案路徑}:{行號範圍} — {這段程式碼的作用}
- ...

🔧 解決方案：

方案 A：{方案名稱}
- 修改：{具體修改內容}
- 優點：{優點}
- 風險：{風險}

方案 B：{方案名稱}（如有）
- 修改：{具體修改內容}
- 優點：{優點}
- 風險：{風險}

📐 影響範圍：
- {會受影響的功能 1}
- {會受影響的功能 2}

🧪 建議驗證步驟：
1. {測試步驟 1}
2. {測試步驟 2}
3. ...

❓ 請確認：
1. 以上分析是否正確？
2. 要選擇哪個方案？（或有其他想法？）
3. 確認後我可以使用 /do-jira-task 開始實作
```

### 7. 等待使用者確認

**重要：分析完成後停在這裡，不會自動開始實作。**

等待使用者：
- 確認分析是否正確
- 選擇解決方案（如有多個）
- 補充額外資訊或提出疑問
- 決定是否要開始實作（可銜接 `/do-jira-task`）

## 分析原則

### 找「根本原因」而非「表面症狀」

❌ 表面症狀：「暱稱設定頁面沒有顯示」
✅ 根本原因：「Firebase Auth session 未清除，導致 `isNewAccount` 判斷錯誤」

### 證據導向

- 每個結論都要有程式碼佐證
- 標明具體的檔案路徑和行號
- 說明程式碼邏輯如何導致問題

### 不猜測，不確定就說不確定

- 如果無法確定 root cause，誠實告知
- 列出所有可能的原因和各自的可能性
- 提出可以進一步確認的方法（如加 log、測試特定場景）

### 考慮完整影響

- 修復方案不能引入新的問題
- 評估修改對其他功能的影響
- 考慮邊界條件和異常情況

## 與其他 Skills 的配合

### 分析後實作
```bash
# 1. 先分析 root cause
/analyze-root-cause EK-1000

# 2. 確認方案後，開始實作
/do-jira-task EK-1000
```

### 分析後建立 PR
```bash
# 1. 先分析 root cause
/analyze-root-cause EK-1000

# 2. 手動修復或用 do-jira-task 修復後
/create-jira-pr-reviewer EK-1000
```

## 適用場景

| 場景 | 說明 |
|------|------|
| Bug 調查 | QA 回報的 bug，需要找出原因 |
| 問題診斷 | 使用者反映的異常行為 |
| 修改前評估 | 動手修改前先了解問題全貌 |
| 技術討論 | 需要向團隊說明問題原因 |
| Crash 分析 | 根據 crash log 追蹤原因 |

## 不適用場景

- 需要直接開始實作 → 使用 `/do-jira-task`
- 已經有 PR 需要 review → 使用 `/review-pr`
- 需要新增功能（非 bug） → 使用 `/do-jira-task`

## 前置條件

- ✅ 已配置 Jira MCP server（如需讀取 Jira issue）
- ✅ 當前在 git repository 中
- ✅ 有足夠的問題描述或重現步驟

## 參數說明

| 參數 | 類型 | 必填 | 說明 | 示例 |
|-----|------|------|------|------|
| Jira URL/Key 或問題描述 | String | 可選 | Jira issue 或問題敘述 | `EK-1000`、問題描述文字 |

如果不提供參數，會詢問你要分析什麼問題。

## 技術實現

此 skill 使用以下工具：

1. **Jira MCP Server (`jira-extended`)** — 獲取 issue 資訊（可選）
2. **Read** — 讀取程式碼檔案
3. **Grep** — 搜尋程式碼中的關鍵字和模式
4. **Glob** — 尋找相關檔案
5. **Agent (Explore)** — 深入探索程式碼庫（複雜問題時使用）
6. **AskUserQuestion** — 需要補充資訊時詢問使用者
